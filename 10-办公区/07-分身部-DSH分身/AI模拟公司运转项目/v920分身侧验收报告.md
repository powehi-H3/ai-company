## T4 原子锁：[通过]（v9.20 核心项）

```sh
$ cat /data/adb/rootd_keeper/state/lock.d/pid
10536

$ cat /data/adb/rootd_keeper/state/rootd.pid
10536

$ ls -la /data/adb/rootd_keeper/state/lock.d/
drwx------ 2 root root 3452 2026-11-16 10:11 .
-rw------- 1 root root    6 2026-11-16 10:11 pid

$ ps -A -o PID,PPID,ARGS | grep rootd-priv | grep -v grep
10536     1 sh /data/adb/modules/rootd_keeper/common/rootd-priv.sh
10689 10536 sh /data/adb/modules/rootd_keeper/common/rootd-priv.sh
10707 10536 sh /data/adb/modules/rootd_keeper/common/rootd-priv.sh
10708 10707 sh /data/adb/modules/rootd_keeper/common/rootd-priv.sh
15300 10536 sh /data/adb/modules/rootd_keeper/common/rootd-priv.sh
```

**证据分析**：

| 检查项 | 结果 |
|---|---|
| 锁 pid == rootd.pid | ✅ 都是 **10536**，完全一致 |
| 真守护数量（ppid=1） | ✅ **只有 1 个**（10536） |
| 其余进程性质 | ✅ 全部是 10536 的子进程 |

**进程树还原**：
```
10536  (ppid=1)  ← 唯一真守护，init 直管
├── 10689        ← 心跳子 shell
├── 10707        ← 命令处理子 shell
│   └── 10708    ← 10707 派生（孙进程，可能是 base64/sed 等）
└── 15300        ← 验收期间我发命令派生的临时进程
```

**为什么这证明 v9.20 修好了**：

旧版 v9.16 的 takeover 逻辑：
```sh
for _p in $(ps -A -o PID,ARGS | grep "rootd-priv.sh" | grep -v grep); do
  case "$_c" in *rootd-priv.sh*) kill -9 "$_p" ;; esac
done
```

这段会**把上面 5 个进程全部 kill -9**，包括正在执行命令的子 shell —— 这就是我之前「杀守护把自己也杀了」的原因。

v9.20 用原子锁：抢到锁的进程（10536）成为唯一守护，其他进程启动时抢锁失败 → 读锁里 pid → 发现存活且心跳新鲜 → **exit 0，不杀任何东西**。

实测结果与此完全吻合：1 个真守护 + 4 个子进程共存，没有互相残杀。

```sh
  重新开启：rootc.py --on
  （只影响本实例，其他实例不受影响）

```

**关键技术指标：92ms 返回**，不是 130 秒超时。

### 开回来

```sh
$ python3 ~/tools/rootc.py --on
分身：已开启（仅本实例）

$ python3 ~/tools/rootc.py 'echo 恢复了'
恢复了

耗时：5485ms
```

**证据分析**：
- `--off` 后立刻报「本实例已关闭」，**92ms** ✅（阈值：不是 130 秒就合格，实际快了 1400 倍）
- 提示语明确说「仅本实例」「不影响其他实例」✅
- `--on` 后恢复正常执行 ✅
- 5485ms 是正常的命令往返（守护 2 秒一轮 + FIFO 轮询），不是异常

**为什么 92ms 这么快**：客户端 `run_once()` 开头有个本地预检 `if os.path.exists(OFF): die(...)`，不等守护响应就返回了。这是 v9.19 加的逻辑，工作正常。

v9.20 的原子锁是好设计，但如果锁文件残留（比如上次进程异常退出没清锁目录），新进程会不会误判「已有守护在跑」而 exit 0？

我在 T4 的锁目录里看到：
```
-rw------- 1 root root 6 2026-11-16 10:11 pid
```
锁目录创建于 10:11，现在 10:33，说明**锁目录是持久的**（守护退出时会 rmdir 吗？）。

**如果守护被 kill -9（来不及清理），锁目录残留 → 下次启动抢锁失败 → 读锁 pid → 该 pid 已死 → 走「精确 kill」分支 → 应该能恢复。** 但这条**我没实测**（不敢杀守护，红线）。

**建议**：如果主体愿意，可以做一次「强杀守护 → 重新启动」的恢复测试，确认锁目录残留不会导致永久起不来。
