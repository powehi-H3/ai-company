# AI公司｜多 AI 协作系统公共仓库

**这是整个多 AI 协作系统的公共工作空间与多个项目的承载仓库，不是任何单一项目的专属仓库。**

当前正在开发的「多 AI 协作与项目管理系统」只是其中一个正式项目。

## 新 AI / 新会话：从这里开始

所有 AI 接入本仓库，按顺序阅读：

1. [AI-协作入口.md](AI-协作入口.md) —— 仓库定位、开工顺序、协作入口。
2. [AI-仓库使用标准.md](AI-仓库使用标准.md) —— 权限、分支、并发、资料保护、审查和交付规则。
3. [AI-仓库目录地图.md](AI-仓库目录地图.md) —— 按实际盘点结构找文件。
4. [AI-规则冲突与兼容表.md](AI-规则冲突与兼容表.md) —— 旧规则冲突、历史前提和待决事项。
5. 再按任务读取公司制度、员工名册、岗位知识和目标项目文件。

自动化、派活、读库、发包或审查任务，先查 `SKILLS.md`，避免重复造轮子。

## 基本规则

- 一个项目一个正式项目目录；项目文档以 `20-项目区/` 为权威来源，工位目录保存角色工作过程。
- 不要把项目方案擅自升级成全局制度。
- 用户授权、GitHub 账号权限、Android 设备权限互不等价；只报告实际可用的能力。
- 默认使用独立工作分支，经过审查再集成；未经用户明确确认，不合并 main、不重写历史。
- 不得静默覆盖、删除、移动原始资料；有冲突先登记并给出兼容方案。
- 所有重要交付写清路径、分支/提交、证据、未完成项和回滚方式。
- GitHub 提交不等于已同步到 Android 手机目录；两种交付必须分别验证。

## 原有制度与历史说明

仓库原有公司制度继续保留。部分规则形成于早期设备权限条件，例如「只有 DSH 能修改公司文件夹」。这类描述不能被简单删除，也不能被误读为所有 AI 永久没有 GitHub 分支写入能力。具体如何兼容，见 [AI-规则冲突与兼容表.md](AI-规则冲突与兼容表.md)。

## 旧规则提示

- 项目 ZIP 位置以 [04-项目打包规则.md](04-项目打包规则.md) 为准：进行中项目包放项目目录根部，不创建 `99-发布包/` 子目录。
- 结项归档按 [10-项目归档规则.md](10-项目归档规则.md) 执行；与档案室重复备份的冲突尚未批准统一前，不要自行删除任何现存副本。
- 员工能力、App 可读性、自动投递状态均是带时间的实测快照；执行任务前需重新确认。
