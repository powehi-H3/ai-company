## 零、一句话结论

**三个轮子里，`dsh-rootd-v4.9.3` 的设计成熟度明显高于我们的 v9.21。**
它有 5 处我们现在没有、而且确实更好的设计。
`dsh-root-bridge` 两件是一套「最小可用」方案，思路极简，有几个巧思值得借鉴。

**我们自己的优势也很明确：主体/分身双实例隔离、原子锁、WebUI 双开关、完整的验收记录。**
这三个轮子**都没有做多实例**，全是只认主体（user 0）。

## 二、值得借鉴的 7 个点（按价值排序）

### ⭐⭐⭐ 1. FIFO 唤醒：空闲时零轮询、零 fork

**轮子**：`dsh-root-bridge-1.3.0/dsh-root.sh`

```sh
# 读写方式打开，避免 open 阻塞
exec 3<>"$FIFO" || exit 1

while true; do
  read -t 5 -r _ <&3 2>/dev/null     # 阻塞等唤醒，最多 5 秒
  run_pending
  ...
done
```

客户端：

```sh
if ! timeout 10 sh -c 'printf "w\n" > "$1"' sh "$FIFO" 2>/dev/null; then
  echo "root 桥没在监听：模块没装、没重启，或屏幕还没解锁" >&2
  exit 124
fi
```

**我们现在**：`while :; do ... sleep 2; done` —— 每 2 秒醒一次，24 小时不停。

**差距**：
| 项 | 我们 v9.21 | 轮子 |
|---|---|---|
| 空闲唤醒 | 每 2 秒一次（43,200 次/天） | 阻塞等 FIFO，有请求才醒 |
| 响应延迟 | 最坏 2 秒 | 立即 |
| 电量 | 持续唤醒 | 阻塞不耗 CPU |
| 客户端快速失败 | 读心跳（20 秒阈值）| **写 FIFO 失败即报错，10 秒内明确说原因** |

**这一条最值得抄。** 而且它顺手解决了另一个问题：客户端能立刻知道「守护没在监听」，不用猜。

---

### ⭐⭐⭐ 2. `doctor` 一键体检：逐项检查 + 自动修复

**轮子**：`dsh-rootd-v4.9.3/bin/rootd-ctl`

```sh
rootd-ctl doctor
```

每项都先检查再**尝试修复**，输出 `ok:` / `FAIL:` / `miss:` / `wait:` 前缀：

```
--- 1. rootfs ---
ok: /data/user/0/.../rootfs
--- 2. 信箱 ---
miss: 自动建 -> /data/user/0/.../mail
--- 3. 配置文件 ---
ok: /data/adb/rootd.conf
--- 4. 容器客户端 ---
ok: /data/user/0/.../rootfs/usr/local/bin/rq
--- 5. 守护进程 ---
miss: 尝试拉起
ok: 已拉起
--- 6. 心跳 ---
ok: 2s 前
--- 6b. 看护 ---
ok: watchdog pid=1234
```

**我们现在**：没有一键体检。出问题要人工逐条查（`cat` 心跳、`ps` 进程、读 `scan.txt`、看 `rejects`）。

**差距**：这是「用户视角」最实用的功能。v9.6 那次我审出「守护没跑时客户端空等 130 秒」，本质就是缺一个自检入口。

---

### ⭐⭐⭐ 3. 自愈：环境缺失自动补齐

**轮子**：`dsh-rootd-v4.9.3/service.sh` + `rootd-watchdog.sh` + `rootd-lib.sh`

三层自愈：

| 层 | 做什么 | 频率 |
|---|---|---|
| `boot_try()` | 找不到信箱就重试引导（建目录、生成令牌、写 conf、装客户端） | 20 次 × 15 秒，之后每 60 秒 |
| 主循环内 | 每 60 轮检查 `rq` 是否还在，不在就重装 | 约 1 分钟 |
| `watchdog.sh` | 守护不在就拉起；每 4 轮顺带补容器环境 | 15 秒 |

**关键洞察**（轮子注释原文）：

> App 重装 / 清数据 / rootfs 重建之后，信箱和 rq、rootd-ctl 会一起消失，
> 只拉守护是不够的 —— 那时守护活着但容器里敲 rq 会 not found。

**我们现在**：`install_client()` 只在扫描实例时调一次。如果 proot rootfs 被重建，客户端就没了，但守护不会补。

**差距**：这是我们一个真实缺口。rootfs 重建（App 重装/清数据）后我们会失效，轮子会自愈。

---

### ⭐⭐ 4. `status` 看板：key=value 结构化状态

**轮子**：`dsh-rootd-v4.9.3/bin/rootd-daemon.sh` 的 `publish()`

```sh
version=rootd v7.0
since=2026-11-16 10:00:00
uptime=3600
pid=1234
uid=0
ctx=u:r:ksu:s0
gate=1
mode=permanent
count=42
last=0
heartbeat=2s
mail=/data/user/0/.../mail
rf=/data/user/0/.../rootfs
client=ok
daemon=alive
```

**还有 `publish_counters()`**：只刷 `count`/`last`/`updated`/`uptime` 四行，不重写整个文件。
注释说明了理由：

> 重写会让 since / uid / ctx 等内容每次变动，也更容易和并发读撞上。

**我们现在**：`instance.json` 只有 role/uid/version/channel 几个静态字段。
运行状态（跑了多少条、最后一次退出码、运行多久）**完全没有**。

**差距**：轮子的状态看板信息密度高得多，而且区分「全量发布」和「增量刷计数」，这是并发友好设计。

---

### ⭐⭐ 5. 「还差什么」直接说出来（`wait=` 字段）

**轮子**：`rootd-ctl status` 尾部

```sh
if [ -z "$RF" ]; then w=rootfs
elif [ ! -d "$M" ]; then w=mailbox
elif ! pgrep -f '...rootd.sh$' >/dev/null; then w=daemon
elif [ ! -x "$RF/usr/local/bin/rq" ]; then w=client
else w=""; fi
echo "wait=$w"
```

注释：

> v4.6.3：把「还差什么」直接说出来，面板就不用猜「读不到状态」到底坏没坏

**我们现在**：`scan.txt` 有 `count=N`，但**没有一个字段直接回答「现在卡在哪一步」**。

**差距**：这正是我们 v9.6~v9.11 反复踩的坑——「找到 4 个候选、0 个实例、没有任何拒绝日志」。
如果有 `wait=` 字段，一眼就能看出卡在哪。

---

### ⭐⭐ 6. 审计日志（记录命令摘要）

**轮子**：`dsh-root-bridge-1.3.0/dsh-root.sh`

```sh
cmd=$(head -c 120 "$f" | tr '\n\r\t' '   ' | tr -d '"' | sed 's/  */ /g')
...
echo "$(date '+%F %T') 执行 $n 命令 \"$cmd\" 退出码 $code" >> "$LOG"
```

**我们现在**：`rootd.log` 记 `dispatch <id>: <命令前200字节>`，**但没有退出码，也没有执行耗时**。

**差距**：轮子的日志更适合审计（能看「这条命令成功没成功」）。

---

### ⭐ 7. 三态闸门（permanent / timed / locked）

**轮子**：`dsh-rootd-v4.9.3` 的 `mode` 文件

| 模式 | 行为 |
|---|---|
| `permanent` | 永久开启 |
| `timed` | 到 `expire` 时间点自动转 locked |
| `locked` | 永久关闭，**重启/重装都保持** |

**我们现在**：只有 `off` 文件（开/关二元）。

**差距**：`timed` 模式有实际价值——比如「临时开 10 分钟让我干个活，到点自动关」。
这是**安全设计**，不是花活。

## 三、我们的优势（这三个轮子都没有）

### ✅ 1. 主体/分身双实例隔离

**三个轮子全部只认 `/data/user/0/`（主体）**，没有一个支持分身。

我们的 `probe_ok()` 6 道校验 + `CLONE_ALLOW="999"` + 每实例独立 `off` 文件，
这套设计是**独有的**。

**但要诚实说**：单实例方案简单得多，我们的多实例复杂度是换来的。
轮子的 `dsh-root-bridge-1.3.0` 只有 5.6KB，我们的 `rootd-priv.sh` 是 37.9KB——**7 倍代码量**。

### ✅ 2. 内核级原子锁（v9.20 引入）

轮子用的是 **PID 仲裁**：

```sh
me=$$
min=$me
for p in $(pgrep -f "$SELF_PAT"); do
  [ "$p" -lt "$min" ] && min=$p
done
if [ "$me" != "$min" ]; then sleep 2; ... exit 0; fi
```

注释（`rootd-daemon.sh`）：

> 之前用 mkdir 锁：两个实例同时启动时，先 mkdir 的那个还没来得及写 pid，
> 后到的读到空值就把锁删了重建 —— 结果两个都在跑。改成比 PID...

**两种方案对比**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **我们的 mkdir 锁** | 原子、内核保证 | 僵尸锁需要额外处理（我们踩过） |
| **轮子的 PID 仲裁** | 不依赖文件系统、天然幂等 | 依赖 `pgrep` 精确匹配（轮子踩过 busybox 前缀的坑，v4.9.3 就是修这个） |

**我们更好**：`mkdir` 是内核原子操作，不依赖 `pgrep` 的正则正确性。
轮子 latest 版本 4.9.3 的更新说明就是「修复守护单实例仲裁漏判 busybox 前缀」——**它还在踩这个坑**。

### ✅ 3. WebUI 双开关

轮子的 WebUI（32KB app.js）功能更丰富（面板、日志、自检、重启），
但**没有双实例开关**，因为它压根没做多实例。

### ✅ 4. 完整的验收记录与版本历史

我们有 `v9.1 → v9.21` 完整归档、验收报告、审查报告、CHANGELOG。
三个轮子**只有 README，没有验收记录**。

## 四、我们的缺点（轮子有、我们没有）

### 🔴 P0：没有 `doctor` 一键体检

出问题只能人工逐条查。**这是用户视角最痛的缺口。**

### 🔴 P0：没有 FIFO 唤醒，每 2 秒空转

24 小时 43,200 次无效唤醒，随时在耗电。

### 🟡 P1：没有环境自愈

proot rootfs 被重建（App 重装/清数据）后，客户端消失，守护不会补回来。

### 🟡 P1：没有运行状态看板

不知道跑了几条、最后退出码是什么、运行多久了。

### 🟡 P1：没有 `wait=` 字段

「现在卡在哪一步」要人工推断。

### 🟡 P1：日志没有退出码

审计时看不出命令成功没成功。

### 🟢 P2：没有三态闸门

只有开/关，没有「限时开启」。

### 🟢 P2：没有把 root 包成 AI 工具

轮子的插件把 root 执行包成 `root_run` 工具，AI 能直接调用并画成卡片。
我们只能靠 `rootc.py` 手敲。

## 五、建议（按性价比排序）

| 优先级 | 做什么 | 收益 | 成本 |
|---|---|---|---|
| **P0** | 加 `doctor` 一键体检 | 用户能自己诊断 80% 的问题 | 中（约 150 行 sh） |
| **P0** | 改 FIFO 唤醒（保留 2 秒兜底） | 省电 + 响应快 + 客户端快速失败 | 中（改主循环 + 客户端） |
| P1 | 加运行状态看板（`count`/`last`/`uptime`） | 出问题好定位 | 低（复用 `instance.json`） |
| P1 | 日志加退出码 | 审计完整 | 极低（一行） |
| P1 | 加 `wait=` 字段 | 一眼看出卡在哪 | 低 |
| P1 | 环境自愈（定期补客户端） | rootfs 重建后不失效 | 中 |
| P2 | 三态闸门 `timed` | 临时授权更安全 | 中 |
| P2 | `root_run` AI 工具 | AI 能直接调 root | 高（要写插件） |

## 六、不建议抄的

| 轮子的做法 | 为什么不抄 |
|---|---|
| **PID 仲裁做单实例** | 依赖 `pgrep` 正则正确性，轮子自己踩了 3 个版本才修对 busybox 前缀。我们的 `mkdir` 原子锁更可靠 |
| **`/data/local/tmp` 放执行脚本** | 那个目录全局可写（`1777`），有被抢注风险。我们用私有 700 目录更好 |
| **令牌放信箱里（`rootd.token` 644）** | 令牌和信箱同目录，能读信箱就能读令牌，等于没保护。我们靠目录 700 权限隔离，更简洁 |
| **轮子的 `chmod 777` 信箱** | `777` 意味着任何 App 都能往里投命令。我们 `700` + `chown` 到实例 uid，安全得多 |
| **一个大 `app.js`（32KB）** | 我们 WebUI 单文件 23KB 已经够用，再大难维护 |

---

## 七、一句话总结

> **轮子的「易用性」比我们强：有体检、有看板、有自愈、FIFO 唤醒省电。**
> **我们的「安全性与严谨性」比轮子强：双实例隔离、内核原子锁、707 权限、完整验收。**
>
> **最该抄的是 `doctor` 和 FIFO 唤醒这两条**，它们直接解决我们踩过的坑。
> 其余可以慢慢补。
