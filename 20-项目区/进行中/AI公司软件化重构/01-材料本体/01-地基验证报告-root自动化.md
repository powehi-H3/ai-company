## 三、所以「自动发消息」到底能不能做

**能做。** 完整链路：

```
1. monkey / am start 启动目标 App          ✅ 已验证
2. sleep N 等加载                          ✅
3. uiautomator dump 抓界面                 ✅ 已验证（4410 元素）
4. 解析 XML 找到输入框坐标                  ✅ 已验证方法
5. input tap 点输入框                      ✅ 命令存在
6. input text "消息内容"                    ✅ 命令存在
7. input keyevent 66（回车）或点发送按钮     ✅ 命令存在
8. dump 再次验证是否发送成功                 ✅
```

**每一步都有对应的命令。不需要无障碍服务、不需要 ADB 授权、不需要改 App。**

## 四、但也必须说清真实的困难

**「能做」不等于「好做」。** 实测暴露了三个真问题：

### 4.1 界面加载时机不确定

**实测**：启动 ChatGPT 后 sleep 4 秒，抓到的界面只有 **110 个元素**，
文字只有「获取 Plus」—— **还没加载完，停在启动页。**

而 DSH 自己的界面有 4,410 个元素。

**结论**：必须做「轮询等待」——反复 dump 直到找到目标控件，不能固定 sleep。

### 4.2 每个 App 的界面结构完全不同

ChatGPT、千问、DeepSeek、豆包、Grok 是**五个不同公司的 App**，
输入框的 `resource-id`、`class`、位置全都不一样。

**结论**：要**为每个 App 单独写适配器**，不能一套通吃。

### 4.3 界面会随 App 更新而变

App 一升级，控件 id 或布局可能变，适配器就失效。

**结论**：适配器要**能自愈**——优先用「语义特征」（如"可编辑且在最底部"）而不是硬编码 id。

## 六、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **发错内容** | 打错字就发出去，撤不回 | **发送前先在界面核对文字**；高危内容二次确认 |
| **发错对象** | 界面没切对就发 | **每次发送前校验前台包名** |
| **App 界面变了** | 升级后适配器失效 | 语义特征 + 失败时降级为「填好不发送」 |
| **被 App 检测为异常** | 可能触发风控 | 加随机延迟，模拟人类节奏 |
| **账号风险** | 自动化可能违反使用条款 | **这个要董事长拍板** |
| **误触其他按钮** | 坐标算错点到别的 | 发送前 dump 校验目标控件 |

---

## 七、我建议的做法（分档）

| 档 | 做什么 | 风险 | 建议 |
|---|---|---|---|
| **保守** | 只做到「填好文字，不点发送」 | 极低 | ✅ 先做这个 |
| **半自动** | 填好 + 高亮，你手动点发送 | 低 | ✅ 推荐日常用 |
| **全自动** | 填好 + 自动发送 + 自动读取 | 中 | ⚠️ 要董事长明确授权 |

**我的建议：先做「保守档」验证稳定性，稳了再升级到「半自动」，全自动由你决定。**

> **董事长说得对。我之前说「物理做不到」是错的。**
>
> **root + `input` + `uiautomator` 完全能实现自动投递消息。**
