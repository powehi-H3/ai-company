# 三个成熟轮子 · 架构调研与整合方案

- 版本：v1.0
- 日期：2026-11-16
- 调研对象：T3 Code / Orca / HarnessHub
- 目的：把 AI 公司项目从「自己瞎造」升级成「站在成熟轮子上的专业产品」

---

## 一、一句话结论

> **我们的项目，本质是一个「Agent 编排器」。编排器这个品类已经有成熟轮子（T3 / Orca）。**
> **我们唯一独特、且没人做过的是：用 root 把 5 个「封闭的手机 App」（ChatGPT/千问/豆包/Grok/DeepSeek）伪造成可被编排的 Agent。**
> **正确的做法不是再造一个编排器，而是把「root 操控封闭 App」做成一个符合 ACP 协议的适配器，喂给现成的编排器。**

---

## 二、三个轮子分别是什么（架构级理解）

### 2.1 T3 Code ——「控制面」（Control Plane）

| 维度 | 内容 |
|---|---|
| 定位 | 开源编程 Agent 控制面板，MIT 协议 |
| 核心架构 | **server（执行环境）与 client（web/桌面/手机）分离**，通过鉴权 RPC 通信 |
| 关键设计 | ① 执行永远在「拥有 workspace 的环境」里，远端 client 不能替换文件系统/凭据 ② 事件溯源：编排状态是 events，projection 是唯一真相 ③ provider 行为藏在 adapter 后，编排器只跟标准化命令/事件打交道 |
| 支持 | Claude Code、Codex、Cursor、Grok Build…以及**任意 ACP agent** |

**最关键的发现**：T3 文档明确写——

> 「For DeepSeek Harness, use `dsh` with arguments `--profile` and `acp`.」

**DeepSeek Harness 自带一个 ACP profile**，能用 `dsh --profile acp` 启动，被 T3 这类控制面板直接接管。

### 2.2 Orca ——「Agent 开发环境」（ADE）

| 维度 | 内容 |
|---|---|
| 定位 | 编排多个 CLI agent，各用独立 worktree，并行跑 |
| 核心能力 | ① 一个大任务交给一个 agent，它拆解、起 worker agent、回收结果（**这正是我们要的「派活→分工→汇总」**）② 手机远程 ③ diff 评审 ④ 独立 worktree 隔离 |
| 支持 | 任何 CLI agent，**列表里直接有 DeepSeek Harness** |

**关键结论**：Orca 已经把「多 agent 并行 + 各自工作区 + 手机远程 + 派活汇总」全部产品化了。我们要做的「多 AI 分工协作」在 Orca 里是现成的。

### 2.3 HarnessHub ——「Agent 打包标准」

| 维度 | 内容 |
|---|---|
| 定位 | Agent 运行时环境的「应用层打包标准」，号称「npm of AI Agent Harnesses」 |
| 核心洞察 | **Docker 能打包「怎么跑」，但不能表达「哪些是模板、哪些是状态、哪些需要重绑」**。HarnessHub 补这个空 |
| 六层架构 | ① 镜像规范层 ② 适配器层 ③ 镜像构建层 ④ 组合层 ⑤ 导入物化层 ⑥ 校验层 |
| 核心工作流 | `inspect → export → import → verify`（.harness 包 = manifest.json + 配置 + 工作区 + 状态 + 凭据，凭据在 template 模式排除） |

**关键洞察**：一个 agent 的「可用状态」= 代码 + 配置 + 记忆 + 凭据。这跟我们公司的「状态 = 文件夹 + 对话 + 规矩 + 脚本」是**同一类问题**——ZIP 只能打包文件夹，打包不了记忆和状态。

## 三、ACP 协议（把三个轮子串起来的那根线）

**ACP = Agent Client Protocol**，定位类似 LSP（语言服务器协议）之于编辑器：标准化「编辑器 ↔ 编码 agent」之间的通信。

| 特性 | 内容 |
|---|---|
| 通信 | JSON-RPC，本地走 stdio，远程走 HTTP/WebSocket |
| 复用 | JSON 表示复用 MCP，另加 diff 显示等 agentic UX 元素 |
| 意义 | **agent 实现 ACP → 任何兼容编辑器都能用；编辑器支持 ACP → 获得整个 agent 生态** |

**对我们的意义**：
- 我们的 DSH（DeepSeek Harness）已经实现了 ACP（`dsh --profile acp`）
- 但 ChatGPT / 千问 / 豆包 / Grok / DeepSeek App 是**封闭的，没有 ACP 接口**
- **我们要做的那一块，就是把封闭 App 包装成一个「伪 ACP agent」**，让它能被 T3 / Orca 这类编排器当作标准 agent 来用

## 四、对照我们的项目：哪些直接用，哪些必须自造

### 4.1 直接借用（不该再自己造）

| 能力 | 用哪个轮子 | 我们现在的做法 | 结论 |
|---|---|---|---|
| 多 agent 并行 + 隔离工作区 | Orca 的 worktree | 文件夹 + 工位（弱隔离） | **该换成 Orca 思路** |
| 派活→拆解→汇总 | Orca 的 orchestration | 全靠董事长手工 | **直接用** |
| 手机远程控制 | T3 / Orca 的移动端 | 我们插件（半成品） | **该用现成** |
| 线程/会话管理 | T3 的 event-sourcing | 我们还没做 | **抄它的事件溯源模型** |
| 控制面与执行分离 | T3 的 server/client 边界 | 我们混在一起 | **抄它** |
| 公司状态打包迁移 | HarnessHub 的 manifest 分层 | 我们只有 ZIP 文件 | **抄 manifest 思想** |

### 4.2 必须自造（我们的独有核心，没人做过）

**一件事，只有一件事：把「封闭的手机 App」伪造成「可编排的 Agent」。**

| 为什么没人做过 | 我们的优势 |
|---|---|
| T3/Orca 管的是 CLI agent，假设 agent 有命令行接口 | 我们的 AI 没有 CLI，只有 App |
| 别人用 ACP 对接的是「能跑命令的进程」 | 我们有 root，能读 App 数据库、能注入 UI 点击/输入 |

**具体要自造的是：一个「App↔ACP 桥接适配器」**

```
封闭 App（ChatGPT/千问/...）
        ↑
  root 适配层（我们已有的：rootc + 读数据库 + ADB 注入）
        ↑
  ACP 协议封装（要新做：把上面的能力翻译成标准 ACP agent 接口）
        ↑
  T3 / Orca 编排器（现成，直接用）
```

## 六、落地方案（分三步，专业路线）

### 第一步：验证 ACP 可行性（半天）

**这是最关键的一步，先做，失败后面全白搭。**

1. 确认 DSH 的 ACP profile 能跑：`dsh --profile acp --help`
2. 确认 T3 Code 能接到它（T3 文档明确说支持 `dsh --profile acp`）
3. 结论分两种情况：
   - ✅ DSH 的 ACP 能通 → 我们的 DSH 本体已经是「标准 agent」，能被编排器接管
   - 然后专注做「App↔ACP 桥接」，让 5 个封闭 App 也变成标准 agent

### 第二步：做「App↔ACP 桥接适配器」（核心，1~2 周）

把已有能力封装成标准接口：

| 已有能力 | 封装成 ACP 的什么 |
|---|---|
| rootc 读 ChatGPT/千问/DeepSeek 对话 | `list_sessions` / `read_session`（ACP 的 session 能力） |
| ADB 注入发送消息 | `send_message` / `prompt` |
| 检测谁回复了 | `session_update` 事件 |

**目标**：让 T3/Orca 看到一个叫 "ChatGPT" 的 agent，能像对待 Claude Code 一样对待它。

### 第三步：打包迁移（借用 HarnessHub）

把「公司」定义成一个 harness image：
- `template`（规则、脚本、目录结构）→ 可共享
- `state`（对话、产出、进度）→ 可迁移
- `credentials`（各 App 登录态）→ 排除，重绑

这样公司能一键复制、备份、迁移到新手机。

## 七、这条路跟「自己造」的本质区别

| 维度 | 自造（旧路线） | 借轮子（新路线） |
|---|---|---|
| 编排器 | 自己写事件流/关系引擎/空间引擎 | 用 Orca 的编排 |
| 控制面 | 自己写插件面板 | 用 T3 的手机/桌面端 |
| 数据模型 | 自己设计 SQLite | 抄 T3 的事件溯源 |
| 打包迁移 | 自己写 ZIP | 抄 HarnessHub manifest |
| **我们真正写的** | 全部都要写 | **只有「App↔ACP 桥接」一个核心** |

**一句话：从「造一艘船」变成「造一个发动机，装到现成的船上」。**

## 八、风险与验证点（诚实）

| 风险 | 应对 |
|---|---|
| ACP 能否稳定对接封闭 App（本质是伪 agent） | 第一步先验证 DSH 的 ACP，再逐步桥接 |
| T3/Orca 是否真能接管我们的 root 能力 | 先跑通最小闭环：用 T3 控制 DSH，完成一个真实任务 |
| 封闭 App 的 ACP 封装是否稳定 | App 改版就失效——保留现有 root 适配器做降级 |
| 是否过度依赖别人 | T3/Orca 都是 MIT，可 fork |

## 十、已验证的关键事实（2026-11-16 实测）

**我们的 DSH 本体，已经是标准的 ACP agent。** 这是整个整合方案的地基，已实测确认：

```sh
$ dsh --profile acp --help
Serve automation clients over Agent Client Protocol stdio.
```

- 官方包 `@deepseek-ai/dsh-acp`：`automation-only Agent Client Protocol server`
- Agent 名：`deepseek-harness-acp`
- 支持 ACP v1 标准方法：`session/new` / `session/list` / `session/resume` / `session/prompt` / `session/update` / `session/cancel` / `session/close` / `request_permission`
- T3 Code 文档明确写：`For DeepSeek Harness, use dsh --profile acp`

**结论升级**：
1. ✅ DSH 本体 → 已经是标准 agent，能被 T3/Orca 直接接管（不用做桥接）
2. ⬜ 5 个封闭 App（ChatGPT/千问/豆包/Grok/DeepSeek App）→ 仍需「App↔ACP 桥接」
3. 我们的核心工作进一步收窄：**只做「封闭 App → ACP」这一层桥接**，其余全用现成轮子

**ACP 服务器的完整能力（官方 README 提炼）**：
- 一个连接可同时跑多个独立会话
- 每个会话独立上下文，KV cache 仅追加
- 支持挂载 MCP 服务器、选模型、选推理强度
- 持久化：跨进程重启能 list/resume/close 会话
- 不支持：删除/fork/transcript 回放/附加目录/交互式 UI（刻意只做自动化）

**这意味着**：我们的「多 AI 分工协作」完全可以用 ACP 实现——每个 AI 是一个 ACP session，DSH 做编排。
