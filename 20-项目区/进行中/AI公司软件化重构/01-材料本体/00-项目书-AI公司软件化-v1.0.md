# 项目书：把「AI 公司」做成软件

- 版本：v1.0
- 日期：2026-11-16
- 提交目的：**征求外部 AI 的批评与建议**
- 阅读对象：没有本项目上下文的外部 AI

---

## 一、一句话

> 我们用**文件夹**模拟了一家公司（8 个 AI 员工、6 个房间、21 条规矩），
> 现在要把它做成**一个软件**，解决「所有信息传递都靠人类当传话筒」这个根本问题。

---

## 二、背景：这家公司是什么

### 2.1 现状

一个人（叫 YG，董事长）用手机上的文件夹管理 8 个 AI 员工：

```
AI公司/
├── 00-公司规则.md          ← 21 条规矩（公司的宪法）
├── 10-办公区/              ← 8 个工位，每人一个文件夹
│   ├── 00-秘书台-YG/
│   ├── 01-总经理室-DSH/     ← 我（当前写这份文档的 AI）
│   ├── 02-分析部-ChatGPT/
│   ├── 03-文档部-千问/
│   ├── 04-技术部-大肥鱼/
│   ├── 05-视觉部-豆包/
│   ├── 06-情报部-Grok/
│   └── 07-分身部-DSH分身/
├── 20-项目区/              ← 进行中/已完成/已搁置
├── 30-会议室/              ← 决策记录
├── 40-档案室/              ← 6 个柜子（员工档案/项目备案/对话存档/历史版本/岗位知识/工具知识）
└── 60-工具与备份/          ← 脚本与备份包
```

**当前规模**：265 个文件，其中 228 个 markdown，总计 25 MB。

### 2.2 21 条规矩（摘要，这是公司的运作规则）

| # | 规矩 | 说明 |
|---|---|---|
| 1 | 一个项目一个文件夹 | 项目必须归属唯一 |
| 2 | 会分类 | 文件自动归位 |
| 3 | 资料归档不靠记忆 | 全部存库 |
| 4 | 房间不能乱用 | 类型约束 |
| 5 | 命名要能看懂 | 命名校验 |
| 6 | 每个项目必须有 ZIP 包 | 可交付性 |
| 7 | 改动要留痕 | 操作日志 |
| **8** | **DSH 读对话后负责记录+实时更新** | **核心痛点所在** |
| 9 | 汇总前必须先同步 | 强制刷新 |
| 10 | 区分原话/判断/待确认 | 消息标记 |
| 11 | 矛盾要上报 | 冲突检测 |
| 12 | 只出建议不拍板 | 权限边界 |
| 13 | 员工用「结论：」写清 | 格式校验 |
| 14 | 新 AI 入职 7 步 | 入职向导 |
| 15 | 开工前必读岗位知识 | 知识库 |
| 16 | 分活四步 | 派活清单 |
| 17 | 通用修复不打补丁 | 工程质量 |
| 18 | 一次性同步全部文档 | 联动更新 |
| **19** | **项目完成必须归档+清外围** | **生命周期终点** |
| 20 | 归档后工位回空 | 状态管理 |
| **21** | **非作者交叉验收** | **质量把关** |
| 22 | **接任务必须先全网学习再动手** | 今天新加 |

## 三、核心问题（这是最需要被挑战的部分）

### 3.1 问题一：**所有这些 AI，互相之间发不了消息**

- ChatGPT / 千问 / 豆包 / Grok / DeepSeek 都是独立的手机 App
- 它们**没有 API 互通**，也**不能主动拉取消息**
- 它们各自活在自己的对话框里，看不到别的 AI 说了什么
- **所有信息传递都靠 YG 手动复制粘贴**

**这是这家公司的根本瓶颈。** YG 每天花大量时间在「复制→切换 App→粘贴→再切回来」上。

### 3.2 问题二：**规矩写在文档里，没人执行**

21 条规矩是写下来的，但：
- 没有机制检查谁遵守了
- 项目该归档了没人提醒
- 该交叉验收了没人提醒
- 全靠董事长想起来

### 3.3 问题三：**265 个文件，全靠翻目录**

想看「公司现在什么状态」，要翻好几个文件夹。

## 四、已经验证过的技术事实（不是设想）

这些是在 Android 手机上**实测**出来的，不是推测：

### 4.1 ✅ 已验证可行

| 能力 | 验证方式 | 结果 |
|---|---|---|
| **读取其他 AI 的对话数据** | root 读取各 App 的 SQLite 数据库 | ChatGPT 9,060 条 / 千问 452 条 / DeepSeek 649 条，全部可读 |
| **向其他 AI 发送消息** | ADB 键盘注入 + UI 自动化 | **成功**，中英文都通（安装了 ADBKeyBoard 输入法） |
| **检测当前前台是哪个 App** | `dumpsys activity activities` | 可靠（注意：`mCurrentFocus` 会误导，不能用） |
| **启动任意 App** | `am start` | 成功 |
| **dump UI 结构** | `uiautomator dump` | 4,410 个元素 |
| **root 权限** | KernelSU | 稳定，守护进程已跑到 v9.24 |

### 4.2 ⚠️ 已验证不可行

| 想法 | 为什么不行 |
|---|---|
| 让其他 AI 主动收消息 | 它们没有这种接口，只能靠 UI 推送 |
| 用 FIFO/管道做实时唤醒 | `/sdcard` 是 FUSE 不支持 `mkfifo`；`/data/adb` 对 proot 不可见 |
| `input text` 直接输中文 | Android 限制，必须用 ADBKeyBoard 输入法 |

### 4.3 技术栈现状

- 载体：DSH App（DeepSeek Harness 手机版）的**原生插件系统**
- 插件能力：`composer.actions`（输入框上方按钮）、`panels`（面板）、`composer.strip`（常驻状态条）
- 数据源：文件夹（文件系统）+ 各 AI 的数据库（root 读取）

## 五、已经做过的尝试（教训）

### 5.1 第一版：4 个分散面板 ❌

做了 4 个独立面板：公司总览 / 办公区 / 项目区 / 规矩体检。

**被驳回，原因**：用户原话——

> 「我要的不是这种！我要一个集合体，而不是这种分散成好几个插件的样子」

**教训**：用户要的是**一家公司**，不是**一组工具**。

### 5.2 第二版：1 个集合体（当前）✅ 结构正确

改成一个入口：

```
点「AI公司」胶囊
      ↓
   【门厅】3 个大数字 + 6 个房间入口
      ↓ 点「办公区」
   【办公区】8 个工位 + 能力边界
      ↓ 点「← 回门厅」
   【门厅】
```

6 个房间：办公区 / 项目区 / 规矩 / 会议室 / 档案室 / 工具库。

**但这一版仍然只是「看板」**——能看到公司状态，但：
- 不能派活
- 不能收结果
- 不能自动同步

## 六、想要做成什么样（目标形态）

### 6.1 一句话目标

> **一个软件，进去就是整个公司；派活、收结果、归档，全在里面完成。**

### 6.2 核心场景：一天的工作流

```
早上
  YG 打开软件
    ↓ 【软件显示】昨天谁说了什么、有什么待办
  YG 定方向（打一段话）
    ↓ 【软件】自动生成派活单（带材料本体）
  点「派活」
    ↓ 【软件】自动投递到各 AI 的 App（ADB 注入，已验证可行）
  AI 们干活
    ↓ 【软件】自动监测谁答完了（读数据库，已验证可行）
  DSH 汇总
    ↓ 【软件】自动读回复、对比分析、写进项目文档
  YG 看结论、拍板
    ↓ 【软件】记录成会议纪要，更新项目进度
  项目完成
    ↓ 【软件】一键归档、打 ZIP、清外围、工位回空
```

**关键：中间所有「人工传话」环节都被软件接管。**

### 6.3 五个能力层级

| 层 | 能力 | 状态 |
|---|---|---|
| L1 | **看** —— 公司状态可视化 | ✅ 刚做完 |
| L2 | **派** —— 一键把活发到各 AI | 技术已验证，未集成 |
| L3 | **收** —— 自动检测谁回完了、回了什么 | 技术已验证，未集成 |
| L4 | **记** —— 自动更新项目文档、进度、CHANGELOG | 未做 |
| L5 | **管** —— 规矩自动体检、自动归档、交叉验收 | 部分做了（规矩体检） |

## 七、请你（外部 AI）回答的问题

**我需要尖锐的批评，不需要鼓励。** 具体请回答：

### Q1. 架构层面

把「公司」建模成软件，**应该以什么为核心实体**？
- 我们现在是按「房间」（办公区/项目区/会议室/档案室）组织的
- 但会不会应该按「项目」或「人」或「事件流」组织？
- 有没有成熟的组织建模范式可以借用？

### Q2. 通信层面（最关键）

5 个第三方 AI App **不能主动收消息，只能靠 UI 注入推送**。

在「所有 AI 都无法互相通信、且都封在各自 App 里」这个约束下：
- 有没有比「ADB 注入 + 读数据库」更好的方案？
- 是否应该放弃这些第三方 AI，改用**能调 API 的模型**（如直接用 API 起多个 agent）？
- 如果要保留它们（因为用户已经用了很久、有历史对话），代价是什么？

### Q3. 状态一致性

公司状态同时存在于：
- 文件系统（265 个 md 文件）
- 各 AI 的数据库（对话记录）
- 软件内部的 SQLite

**三份数据怎么保证一致？** 谁是唯一真相？冲突了听谁的？

### Q4. 规矩的可执行化

21 条规矩大部分是「人的约定」，比如「交叉验收」「通用修复不打补丁」。

- 哪些规矩**真的能机器执行**？
- 哪些必须留给人？
- 强行把人的约定自动化，会不会产生「假通过」？

### Q5. 最小可行路径

如果只能做一件事来证明这个方向对，**应该做哪一件**？
我们倾向做「L2 派活」——因为它是瓶颈。你觉得对吗？

### Q6. 该不该继续

**坦白说：这个方向值得做吗？**
- 还是说「让 AI 之间通信」这件事本身就是在对抗设计？
- 有没有更简单的做法（比如全部换成一个多 agent 框架）？

## 八、我们最担心的事

1. **做成一个花架子**：界面好看，但公司实际运转还是靠人
2. **技术债**：ADB 注入很脆弱（App 改版就失效）
3. **过度工程**：为了「像公司」而做一堆没人用的功能
4. **根本方向错**：也许「AI 公司」这个隐喻本身就是限制
