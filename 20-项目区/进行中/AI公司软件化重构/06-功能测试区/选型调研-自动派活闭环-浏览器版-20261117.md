## 零、需求复述（我们到底要什么）

当前缺口：**派活闭环**——发消息给 AI → 自动等回复 → 自动读回 → 自动归档。现在人工介入三次。

技术约束：
- 运行在 Android 手机 proot Ubuntu（无 GUI，无 Docker 常驻）
- 主 AI 是 DSH（本机已有 `acp` profile）
- 其他 AI：ChatGPT / 千问 / 豆包 / Grok（封闭 App，无协议入口）
- 已有资产：rootc（root 通道）、send_intent（intent 投递）、timeline/relation 引擎、事件流

## 二、筛选出的最优 3 个

### 🥇 方案 A：openclaw/acpx —— 推荐作为主力

| 维度 | 评估 |
|---|---|
| **Star / 活跃** | 3,437★，**8 小时前更新**（本次检索时），持续迭代 |
| **协议** | **MIT**（最宽松，商用/闭源改造均可） |
| **技术栈** | TypeScript，Node ≥22.13（本机 Node 24.22 ✅） |
| **部署门槛** | **最低**：`npm i -g acpx` 一条命令 |

**✅ 可直接上线使用的模块**
| 能力 | 说明 |
|---|---|
| 会话管理 | `sessions new` / 持久化 / resume |
| 一次性执行 | `exec`（发出去→自动等→返回结果） |
| 结构化输出 | JSON，机器可读（直接喂给我们的引擎） |
| 权限控制 | permissions 机制 |
| DSH 适配 | `acpx deepseek-harness …`，官方内置 profile |
| 多 agent | 30 个内置 profile（codex/claude/gemini/cursor/…） |

**🔧 需二次开发**
| 模块 | 工作量 | 说明 |
|---|---|---|
| 派活编排 | 1-2h | 包一层：任务 → `acpx deepseek-harness exec` |
| 结果落库 | 1h | 解析 JSON → 追事件流（timeline-engine 已有） |
| 失败重试 | 2-3h | 超时/失败判断 + 重试 + 死信 |
| 任务状态机 | 2-4h | 待发→已发→已回→已归档（可参考 agent-hub 设计） |

**💰 预估改造成本：1 人天**（DSH 单 AI 闭环）／**3-5 人天**（含多 AI）

**⚠️ 隐藏风险**
1. **pre-1.0**：README 明写"CLI 与运行时接口演进中"——升级可能破坏兼容
2. **只覆盖有 ACP 服务端的 agent**：chatgpt/千问/豆包/Grok 是封闭 App，**接不了**
3. **provider 凭据独立**：文档明确"ACP 连接成功 ≠ 模型可用"，需先在 dsh 配好
4. **无任务队列**：acpx 只管"执行一次"，不管"排队/重试/依赖"——需自己补
5. **无审计**：需自己在外面包审计层

## 四、结论与建议

### 推荐组合：**A 主力 + B 兜底 + 借鉴 C 的设计**

```
DSH 任务      → acpx（协议级，稳定，1人天）        ← 主力
封闭App任务   → uiautomator2（UI级，3-5人天）      ← 后续按需
任务队列/重试 → 自己补，但参考 mjolnir 的架构设计   ← 不引入，只学
```

### 为什么
1. **acpx 根治了"界面变就崩"**——根本不碰界面
2. **DSH 是总经理**（最核心），先做它的闭环，价值最大
3. **封闭 App 没有 ACP 服务端**，只能 UI 自动化，且"回复完成判定"仍是硬骨头
4. **mjolnir 功能最强但过重**，且在 Android proot 跑 Rust daemon 风险大，还有**默认外发数据**的隐私红线——只借鉴设计，不引入
