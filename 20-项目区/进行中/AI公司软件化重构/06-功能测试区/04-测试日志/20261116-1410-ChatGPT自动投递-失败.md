# 测试日志 · 2026-11-16 · ChatGPT 自动投递（失败，L1）

- 时间：2026-11-16 14:20~14:30
- 测试人：DSH
- 目标：`com.openai.chatgpt`
- 目的：验证能否自动把文字打进 ChatGPT 并发送

## 二、根本原因（已确证）

### 证据链

```
$ am start -n com.openai.chatgpt/...
启动后前台: io.github.ccch1mneyyy.dsh_app/.LauncherMist  ← 立刻被抢回

$ dumpsys activity activities | grep topResumedActivity
topResumedActivity=ActivityRecord{... io.github.ccch1mneyyy.dsh_app/.LauncherMist ...}
                                                     ↑ 真正 resumed 的是 DSH
```

### 为什么

| 事实 | 后果 |
|---|---|
| 我的命令由 **DSH 的 root 守护**执行 | 命令运行时 DSH 是活跃进程 |
| DSH 是**前台 App** | 每次执行命令，系统把 DSH 提到前台 |
| `mCurrentFocus` 显示 ChatGPT 是**假象** | 它只是有焦点声明，`topResumedActivity` 才是真的 |
| `input` 事件发给**真正的前台** | 所以点击和打字都打进了 DSH |

### 关键教训

> **`mCurrentFocus` 不可信，必须看 `topResumedActivity`。**
> 这两个在本次测试里给出了矛盾结果，前者误导了我。

## 四、这个障碍是根本性的吗

**需要分情况：**

### 情况 A：我的命令由守护执行 → 抢焦点 → **做不到**

这是当前架构。**结论：在当前架构下，自动投递不可行。**

### 情况 B：命令脱离 DSH 上下文 → 可能做到

| 方案 | 原理 | 可行性 |
|---|---|---|
| **计划任务（cron/at）定时执行** | 命令由 init 或 cron 触发，不在 DSH 前台时 | ⚠️ 需验证 |
| **开机脚本** | 同理 | ⚠️ 但需要重启 |
| **分身执行** | 分身也是 DSH App，同样问题 | ❌ |
| **Termux 独立进程** | 如果我们有 Termux | ⚠️ 需确认 |
| **电脑端的 adb** | 通过 ADB 从电脑发命令 | ✅ 一定可行，但需要电脑 |
| **另一台手机 adb 控制** | 同理 | ✅ 但需要设备 |

### 情况 C：不抢焦点的操作 → 可行

| 操作 | 会不会抢焦点 |
|---|---|
| 读数据库 | ✅ 不会 |
| `dumpsys` 读状态 | ✅ 不会 |
| push/pull 文件 | ✅ 不会 |
| **`input tap/text`** | ❌ **会** |

## 五、诚实结论

| 项 | 结论 |
|---|---|
| 抓界面 | ✅ 能做到（但要在目标 App 真在前台时） |
| 启动其他 App | ⚠️ 能启动，但立刻被抢回 |
| **自动投递到 ChatGPT** | ❌ **在当前架构下做不到** |
| 读数据库 | ✅ 不受影响（不抢焦点） |

**不能声称「自动投递可用」。等级 L1。**
