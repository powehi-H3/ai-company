# 开源项目选型调研 · AI公司自动派活闭环

日期：2026-11-17　执行人：DSH
需求背景：当前缺"派活闭环"——发消息给 AI → 自动等回复 → 自动读回 → 自动归档。人工介入三次。

---

## 零、核心发现（改变了整个方案）

**`openclaw/acpx` 原生支持 `deepseek-harness`，且本机 `acp` profile 已存在。**

```bash
# acpx 官方文档明确列出：
acpx deepseek-harness exec 'summarize this repository'
acpx deepseek-harness sessions new
# 默认命令: dsh --profile acp
```

本机验证：
```
/root/.dsh/profiles/acp/package.json
  bundles: ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-acp-app"]  ← ACP 服务端已装
```

**意义**：不需要 UI 自动化，不需要坐标点击，不需要读数据库。
直接走 ACP 协议 → 结构化输入输出、会话持久化、机器可读 → **派活闭环的最优解**。

## 二、筛选出的最优 3 个

### 🥇 方案 A：acpx（ACP 协议直连）—— **强烈推荐**

| 项 | 评估 |
|---|---|
| **Star / 活跃** | 3,437★，**当天更新**，pre-1.0 但活跃 |
| **协议** | **MIT**（最宽松，商用无限制） |
| **技术栈** | TypeScript / Node ≥22.13（本机 Node 24.22 ✅） |
| **部署门槛** | **极低**：`npm install -g acpx` 即可 |

**可直接上线使用的模块**：
- ✅ 会话管理（`sessions new` / 持久化）
- ✅ 一次性执行（`exec`，自动等回复）
- ✅ 结构化输出（JSON，机器可读）
- ✅ 权限控制（permissions）
- ✅ DSH 官方适配（`deepseek-harness` profile 内置）

**需二次开发的部分**：
| 模块 | 工作量 | 说明 |
|---|---|---|
| 派活编排 | 小（1-2h） | 包装 `acpx deepseek-harness exec`，把任务发出去 |
| 结果落库 | 小（1h） | 解析 JSON 输出 → 追加事件流（已有 timeline-engine） |
| 失败重试 | 中（2-3h） | 超时/失败判断 + 重试策略 |
| 多 AI 适配 | 中（视情况） | ChatGPT/千问/豆包/Grok **不在** acpx 支持列表 → 需另想办法 |

**预估改造成本**：**1 人天**（仅 DSH 单 AI 闭环）；多 AI 全支持 ≈ 3-5 人天

**隐藏风险**：
1. ⚠️ **pre-1.0**：README 明写"CLI 和运行时接口演进中"，升级可能破坏兼容
2. ⚠️ **仅覆盖 DSH**：chatgpt/千问/豆包/Grok 这些**封闭 App** 不在 30 个 profiles 里（它们没有 ACP 服务端）
3. ⚠️ **ACP 会话需要 provider 凭据**：文档明确"ACP 连接成功 ≠ provider 可用"，需先在 dsh 配好模型
4. ⚠️ **session resume 有限制**：官方 ACP 服务端不实现 `session/load`，只支持 resume 非活跃会话

### 🥈 方案 B：uiautomator2 + 现有 send_intent.py 升级

| 项 | 评估 |
|---|---|
| **Star / 活跃** | 8,511★，当天更新，2017 年至今持续维护 |
| **协议** | **MIT** |
| **技术栈** | Python（本机已装 ✅） |
| **部署门槛** | **极低**：`pip install uiautomator2` |

**可直接上线的模块**：
- ✅ 元素定位：`d.xpath('//*[@text="发送"]')` —— 语义查询，**比我现在的 XML 手撸稳得多**
- ✅ 等待机制：`click(timeout=10)` —— 自带轮询等待
- ✅ 结构化读取：`.text` 直接取值
- ✅ 跨 user 操作（配合现有 rootc）

**需二次开发**：
| 模块 | 工作量 | 说明 |
|---|---|---|
| 替换 send_intent 的解析层 | 中（3-4h） | 我现在的 `ElementTree` 手撸 → 换 u2 的 xpath |
| 回复检测（关键） | **大（1-2天）** | 需判断"AI 回复完了"：对比消息数变化 / 找结束标志 / 超时兜底 |
| 多 App 适配 | 大（每个 1 天） | ChatGPT/千问/豆包/Grok 界面各异 |

**预估改造成本**：**3-5 人天**

**隐藏风险**：
1. ⚠️ **回复检测不可靠**：AI 流式输出，何时算"完成"没有稳定信号；只能靠"输入框重新可用"或超时
2. ⚠️ **App 改版即失效**：这正是你批评过的老问题，u2 只是让它更稳，不是根治
3. ⚠️ **中文输入仍需 ADBKeyboard**：现有方案保留
4. ⚠️ **199 个开放 issue**：维护负担不小

## 三、对比与结论

| 维度 | A: acpx | B: uiautomator2 | C: mobile-mcp |
|---|---|---|---|
| 协议友好 | **MIT** | MIT | Apache-2.0 |
| 活跃度 | 当天 | 当天 | 6天前 |
| 部署难度 | **最低** | 低 | 中 |
| 改造成本 | **1 人天** | 3-5 人天 | 4-6 人天 |
| 能覆盖 DSH | ✅ | ✅ | ✅ |
| 能覆盖封闭App | ❌ | ✅ | ✅ |
| 稳定性 | **高**（协议级） | 中（UI级） | 中（UI级） |
| 根治"界面变就崩" | **✅ 根治** | ❌ 缓解 | ❌ 缓解 |

### 推荐路线

**主方案 A（acpx）** + **兜底方案 B（uiautomator2）**：

```
DSH 任务      → acpx（协议级，稳定）      ← 主力
封闭App任务   → uiautomator2（UI级，兜底）  ← 不得已时用
```

**理由**：
1. acpx 根治了"界面变就崩"——因为它根本不碰界面
2. DSH 是本公司的总经理（最核心的 AI），先把它做成闭环，价值最大
3. 封闭 App（ChatGPT/千问等）没有 ACP 服务端，只能继续用 UI 自动化
4. 两者都能用 MIT 协议，无法律风险
