# 最优搭配方案 · AI公司技术栈（2026-11-17）

## 一、先回答"能不能直接用 Paperclip"

**技术上可行，但有两个硬门槛：**

| 门槛 | 实际情况 | 判断 |
|---|---|---|
| Node 版本 | 要求 **≥24.11**，本机 **24.22** | ✅ 满足 |
| 部署模式 | `local_trusted`（单机免登录） | ✅ 符合我们场景 |
| 数据存储 | 需确认（文档未明写，但需持久化任务/审计） | ⚠️ 待验证 |
| **费用** | 官方明写"试用 $5-20，活跃公司 **$20-100/月**" | ⚠️ **要花钱** |
| **依赖** | 需要 Claude Code 或 Codex **装在同一台机器** | ❌ **我们只有 DSH** |
| 重量 | Node server + React UI + pnpm workspace | ⚠️ 手机上偏重 |

**最关键的问题**：Paperclip 的 adapter 官方支持 `claude_local` / `codex_local`，**没有 `dsh_local`**。要用 DSH，得自己写 adapter（工作量未知，可能 1-3 天）。

## 二、最优搭配（推荐）

**核心思路：不搬整套，只抄三个机制 + 保留我们的记忆层优势**

```
┌─────────────────────────────────────────────────┐
│  第 1 层：组织层（抄 Paperclip 的三个机制）        │
│  ├─ Heartbeat 心跳    → 解决"必须人传话"          │
│  ├─ Org Chart 组织图  → 工位升级为角色/权限实体    │
│  └─ Approval 审批      → 扩展我们已有的 consent    │
├─────────────────────────────────────────────────┤
│  第 2 层：通信层（acpx）                          │
│  └─ acpx deepseek-harness → DSH 走 ACP 协议       │
│     （封闭App 用现有 send_intent.py 兜底）        │
├─────────────────────────────────────────────────┤
│  第 3 层：记忆层（我们已有的，别动）               │
│  ├─ timeline-engine.js → 事件流（append-only）    │
│  ├─ relation-engine.js → 关系图 + 反向查询        │
│  └─ 问题池 → 任务来源                             │
├─────────────────────────────────────────────────┤
│  第 4 层：展示层（我们已有的 Cordis 插件）         │
│  └─ 总览/项目/文档/团队/制度/公司/上帝视角         │
└─────────────────────────────────────────────────┘
```

### 为什么这样配

| 层 | 用什么 | 理由 |
|---|---|---|
| **组织层** | 抄 Paperclip 机制 | 它有 114k★ 验证过，但整套太重；只抄心跳+组织图+审批三个核心 |
| **通信层** | **acpx** | MIT、原生支持 DSH、1 人天、根治界面问题 |
| **记忆层** | **我们的（保留）** | 事件流+关系图做得比多数项目细，是优势不该丢 |
| **展示层** | **我们的 Cordis 插件** | 已经能跑，7 个 tab 都在用 |

### 不选的东西及理由

| 不选 | 理由 |
|---|---|
| Paperclip 整套 | 依赖 Claude Code/Codex，没有 DSH adapter；$20-100/月；手机偏重 |
| mjolnir | Rust + 默认外发数据（隐私红线） |
| uiautomator2 | 只作封闭 App 兜底，不做主力 |
| AionUi | 面向桌面协作，不是公司治理 |

## 三、落地顺序（4 步，约 5-7 人天）

### 第 1 步：Heartbeat 心跳（1-2 天）★最高优先级
**解决**：AI 之间发不了消息、必须人传话
**做法**：
1. 建 `心跳队列`（SQLite 或 jsonl）
2. 任务产生 → 入队（带 assignee）
3. 定时/触发 → 唤醒对应 AI（DSH 走 acpx，其他走 send_intent）
4. AI 完成 → 回写入队记录 → 自动归档事件流

**验收**：提一个任务给 DSH，不用我说话，它自己做完并归档

### 第 2 步：acpx 接入（1 天）
**解决**：DSH 通信从"UI 点击"变"协议调用"
**做法**：`npm i -g acpx` → 验证 `acpx deepseek-harness exec "echo test"` → 包装成脚本

### 第 3 步：Org Chart 组织图（1-2 天）
**解决**：工位只是文件夹，没有角色/权限/汇报线
**做法**：
1. 给 `03-员工名册.md` 加结构化字段（角色/上级/权限/预算）
2. 关系图增加 `汇报线` 边
3. 插件「团队」页显示组织架构

### 第 4 步：Approval 审批扩展（1 天）
**解决**：重要动作没人把关
**做法**：扩展现有 `consent` 机制 → 支持"多级审批"（如 DSH 提议 → YG 批准）

## 四、成本与风险

### 成本
| 项 | 成本 |
|---|---|
| 开发 | 5-7 人天 |
| 运行 | **0 元**（不引入 Paperclip 的 API 开销） |
| 维护 | 低（都是我们自己的代码 + MIT 轮子） |

### 风险
| 风险 | 等级 | 应对 |
|---|---|---|
| acpx pre-1.0 接口变 | 中 | 锁版本，包装一层隔离 |
| 封闭 App 仍要 UI 自动化 | 中 | 接受，作为已知限制 |
| 心跳机制设计不当 → 死循环 | **高** | 加"最大重试次数 + 人工兜底" |
| 手机性能 | 低 | 我们比 Paperclip 轻得多 |

## 五、如果一定要用 Paperclip

**唯一可行路径**：先在电脑上跑（$20-100/月），验证概念，再决定是否移植。

**不建议在手机上直接跑**，因为：
1. 没有 DSH adapter，要自己写
2. Node server + pnpm workspace 在 proot 里负担重
3. 费用不可控

---

## 六、一句话结论

> **最优搭配 = Paperclip 的组织思想 + acpx 的通信 + 我们自己的记忆层和界面。**
> **不搬整套，只抄三个机制（心跳/组织图/审批），5-7 天落地，0 运行成本。**
