### 🏆 标杆：paperclipai/paperclip —— **就是"AI 公司"这件事本身**

> **官方原文：「If OpenClaw is an employee, Paperclip is the company.」**
> （如果 OpenClaw 是员工，Paperclip 就是公司）

| 项 | 数据 |
|---|---|
| **Star** | **114k** |
| **最近更新** | **5 分钟前**（8,177 commits） |
| **协议** | **MIT** |
| **技术栈** | Node.js server + React UI |
| **支持 agent** | OpenClaw / Claude Code / Codex / Cursor / Gemini / OpenCode / Pi / **Hermes + Gateway** / Grok Build / Kimi |
| **定位** | "管理 AI 员工的开源应用" / "AI agent 团队编排" |

**它的四大支柱（正好对应我们公司要的东西）**：

| 支柱 | 内容 | 我们有吗 |
|---|---|---|
| **Agentic Task Manager** | 任务、审批闸门、可审计流程、从 diff/截图/测试验证 | ⚠️ 部分（问题池+审计） |
| **Org Chart for Agents** | **人+agent 混合组织架构图**、角色、权限、边界、委派、治理 | ❌ **完全没有** |
| **Agent Employee Training** | Skill Studio、共享技能、评测、版本历史、绩效评估 | ⚠️ 部分（SKILLS.md） |
| **Agentic OS** | 跨 provider 运行时、沙箱、MCP、SSO/RBAC、成本控制 | ❌ 没有 |

**核心机制（直接可借鉴）**：
- **Heartbeat（心跳）**：agent 被唤醒做活——"**只要能收到心跳，就能被雇佣**"
- **Org Chart（组织架构图）**：agent 有 boss、title、job description
- **Goal Alignment（目标对齐）**：任务挂到公司目标，agent 看到"为什么"
- **Atomic task checkout（原子任务领取）**：防止两个 agent 抢同一个任务
- **Budget & Cost Control**：公司/agent/项目三级预算，超支自动暂停
- **Governance & Approvals**：审批流、决策追踪、agent 暂停/恢复/终止
- **Routines & Schedules**：定时任务，每次运行生成可追踪的 issue

**它的部署方式**：Node.js server + React UI，Docker 可部署，**手机也能管**

## 三、我们公司 vs Paperclip 对照

| 维度 | 我们（AI公司） | Paperclip | 差距 |
|---|---|---|---|
| **组织架构** | 文件夹模拟（10-办公区/8工位） | Org Chart（角色/汇报线/权限） | ⚠️ 有形状没机制 |
| **任务系统** | 问题池 md | Issue + 评论 + 依赖 + 附件 | ⚠️ 差很远 |
| **派活** | 手动 send_intent | Heartbeat 自动唤醒 | ❌ **核心缺失** |
| **审批** | 无 | 审批阶段 + 决策追踪 | ❌ **核心缺失** |
| **预算** | 无 | 三级预算 + 超支暂停 | ❌ 缺失 |
| **技能** | SKILLS.md（手写） | Skill Studio + 版本 + 评测 | ⚠️ 有雏形 |
| **记忆** | 事件流 + 关系图 | 任务上下文 + 运行历史 | ✅ **我们做得不错** |
| **多 agent** | 8 个（4个能读） | 10+ 种 adapter | ⚠️ 数量少但够用 |
| **部署** | 手机 proot | Node server + Docker | ⚠️ 我们更轻 |

**结论**：
- ✅ **我们的记忆层（事件流+关系图）做得比大多数项目细**
- ❌ **但组织层几乎是空的**——没有真正的"任务派发、审批、预算、心跳"

## 四、三个可选方向（等你定）

### 方向 A：**直接用 Paperclip**（最快，1-2 天）
- 部署 Paperclip（Node server + React UI）
- 把 DSH 接成 adapter
- 优点：立刻拥有组织架构、任务、审批、预算、心跳
- 缺点：
  - 要跑 Node server（手机上重）
  - 我们的文件夹结构要迁移
  - 我们的记忆层（事件流/关系图）要重新对接
  - **可能水土不服**（它是给"20个Claude Code终端"设计的）

### 方向 B：**照 Paperclip 抄，补我们的组织层**（推荐，3-5 天）
只抄三个最关键的机制，不动现有结构：
1. **Heartbeat 心跳**：任务能被"唤醒"给某个 AI（替代现在的"人传话"）
2. **Org Chart 组织图**：把 8 个工位从"文件夹"升级成"有角色/权限/汇报线的实体"
3. **Approval 审批闸门**：重要动作要人批（我们已有 consent，可扩展）

优点：轻、贴合现状、保留我们的记忆层优势
缺点：抄得对不对要靠自己判断

### 方向 C：**继续现在的路，先补派活闭环**（最小，1 天）
就用 acpx 把 DSH 的派活跑通，其他先不管。
优点：马上能用
缺点：**还是没解决"公司"的问题**，只是让传话自动了一点

## 五、我的建议

**B（照抄）**，理由：
1. Paperclip 已经证明了这套东西该怎么做（114k★，5分钟前还在更新）
2. 但全套搬过来太重（Node server + Docker + 迁移）
3. 我们**已经有记忆层优势**（事件流/关系图），缺的是组织层三件套
4. 抄三个机制比搬一个系统快得多，也更贴合手机环境

**如果只能先做一件事，我建议先做 Heartbeat** —— 因为"AI 之间发不了消息、必须人传话"是你公司当前最大的瓶颈，Paperclip 的心跳机制正是解这个的。
