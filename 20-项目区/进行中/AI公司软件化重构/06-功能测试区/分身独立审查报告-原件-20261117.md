## 摘要（结论先行）

这套资料**方向正确、纪律意识极强、留痕文化罕见地完整**，但**文档一致性已经失控**：员工数在 7 / 8 / 9 三个数之间打架、核心指标「对话 92」与明细「94」对不上、底层前提「AI 之间发不了消息」已被自家软件化进度推翻却没同步。这些问题直接击穿了公司自己定的验收尺子——「断上下文、隔一周、换 AI，10 秒接上」——新用户第一步就会被三个互相矛盾的数字带偏。

**最值钱的**是「规矩 + 岗位职责 + 留痕 + 交叉验收」这套把 AI 当公司治理的**元纪律**，尤其规矩十七（通用修复）、二十一（交叉验收）、二十二/二十三（先学再做），以及关系引擎对「参与证据 vs 工位模板」的甄别意识——这是从无数次血泪里长出来的、可复用的方法论。

**最该补的**是：先做一次「全量事实口径统一」（员工数、对话数、状态标记、ZIP 位置、路径），把 02/04/07/08 等被引用却缺失的文档补齐并纳入版本控制，再谈新功能——否则每加一个引擎，旧文档里的旧数字就多一批互相打架的「事实」。

## 一、用户视角审查

### 1. 我能用吗？

**门槛偏高，且第一步就被误导。** 新用户按 README「从哪开始看」的第一条是读 `02-环境布局.md`（全景 L956），但**这份文件根本不在资料包里**；同理 `04-项目打包规则.md`、`07-根因与通用修复原则.md`、`08-项目启动与交付标准流程.md` 都被公司规则引用，却全部缺失。用户拿着一份「全景包」却缺了 4 份被反复引用的关键文档，没法闭环。

更致命的是数字对不上：名册标题写「共 9 位（1 人类 + 8 AI）」（全景 L561），介绍里写「员工（AI）已到位 7 位」（全景 L543），README 树状图又写「8 个工位」（全景 L977）。用户连「这公司到底几个人」都得不到唯一答案。

### 2. 入口好找吗？

**文档入口清晰，产品入口矛盾。** 阅读顺序（README L955、介绍 L551）本身设计得不错。但产品入口（网页控制台）的定位在文档里自相矛盾：`00-主线与进度.md` 说源码在 `60-工具与备份/插件-ai-company-web/`（全景 L1102），`安装说明.md` 却要用户「把本目录复制到 `/root/插件工作区/ai-company-web/`」（全景 L1256-1259）。用户照安装说明找不到「本目录」到底指哪。安装用 `pnpm add`（全景 L1268）、卸载却用 `dsh plugin --profile web remove`（全景 L1345），两套机制是否互相清得干净没有说明。

### 3. 哪里让我困惑 / 失望？

- **「必须人传话」的立身之本已经被推翻，但没人改口径。** 介绍（全景 L516）、名册（全景 L594）、README「一条核心事实」（全景 L1051）反复强调「AI 之间发不了消息、所以需要你传话」，但 CHANGELOG 里「千问自动投递跑通」（全景 L1428）和主线「通信已通」（全景 L1065）说明自动投递已经做出来了。用户会困惑：我到底还要不要当传话员？
- **规则从「三条」膨胀到「二十三条」，介绍却还停留在三条。** 介绍「公司的规矩（三条）」（全景 L524）只写了 3 条；README 标题叫「三条核心规则」却列了 4 条（全景 L1021-1037）。实际规则文档有 23 条，且二十二、二十三两条内容高度重叠。
- **员工能力是「写的」还是「测的」分不清。** 速查表写 Grok「有联网」（全景 L704）像已核实的事实，但名册里 Grok 是「⚠️ 待深挖（数据位置未确认）」（全景 L672）；豆包在名册是「⚠️ 待观察」（全景 L656），在协作清单里又斩钉截铁写「❌ 数据私有加密/本地无明文」（全景 L888）。同一个能力，一份文档说「不知道」，另一份说「确定不能」，违反自家规矩十「不臆造」。
- **大量悬空编号**：`Q-08`、`Q-05`、`Q-06`、`Q-07`、`Q-11`、`R2`、`R3`（全景 L877/891/926/932/941）在资料包里没有任何图例或定义，读者无法追溯这些「硬约束」的出处。

## 二、专业视角审查

### 1. 架构

**单点故障（SPOF）严重。** DSH 被定义为「唯一全知节点 + 唯一能改文件夹」（全景 L586、L728），所有写文件、归档、汇总都压在它一个身上。分身虽有 root 能力（速查表「有 root，能跑命令」，全景 L711），但其读他人对话「未授权，当前不开」（全景 L690）、写文件「仅 root 通道」（全景 L692），且没有任何强制访问控制——全靠文档里的一句「当前不开」自觉。一旦 DSH 不可用或上下文丢失，整个公司停摆。

**「参与」的判定有真功夫，值得肯定。** 关系引擎把「办公区工位（预置模板）」和「实际参与（对话共现证据）」区分开（全景 L1091-1092），避免了把空模板当成工作成果，这是正确的数据建模。

### 2. 数据流

**主链路有断点与矛盾。** 核心数据流是「各 App 对话 → DSH 读库 → 归档 → 关系引擎 → 查询」。但这条链路上：

- 对话数对不上：关系查询「问题一」列 ChatGPT 12 个、千问 3 个、大肥鱼 79 个，合计 **94**（全景 L1153-1155）；同一文件「问题二」和审查报告却写「对话 **92**」（全景 L1163、L1196）；审查报告自己的验证公式是 `deepseek79 + chatgpt10 + qwen3 = 92`（全景 L1196），即 ChatGPT 是 **10** 个，与关系查询的 **12** 矛盾。
- 「会话」与「对话」口径不一：名册写千问「4 会话 452 条」（全景 L624），关系查询写千问「3 个关联对话」（全景 L1154）。两个单位如何换算，没有说明。

### 3. 隐私

**读的是用户自己设备上其它 App 的数据库原文，但缺最小化与授权清单。** 名册明确记录了「DSH 有 root，能读其他 AI 的数据库」（全景 L592），并列出 ChatGPT 9060 条、千问 452 条、大肥鱼 649 条（全景 L608/624/640）——即通过 root 抓取第三方 App 的本地库。豆包 454MB 数据「位置未确认」却仍在被探查（全景 L656）。审查报告声称「产物 0 绝对路径、对话原文 git 追踪数 0」（全景 L1198）做到了产物脱敏，但**采集端没有**：读谁、读多少、读到什么敏感内容、是否最小化、有没有审计清单，全部没有。这属于「自己做得到、但缺管控」的隐私风险，不是做不到。

### 4. 幂等

**引擎层做得不错，文档层不幂等。** 关系引擎「read model 可整体重建、事实源不变（CQRS）」、边数稳定 252「重复跑不增长」（全景 L1095、L1195）说明代码层幂等做到了。但**文档层不幂等**：同一事实（员工数、对话数、ZIP 位置）在不同文档里重复书写且不同步更新，导致「以哪份为准」无法判定——这正是规矩十八（改动后一次性同步全部文档）要治的病，但这份资料包本身没治好。

### 5. 文档一致性（本包最大短板）

见下方问题清单，是 P0/P1 最密集的区域。

### 6. 可持续性

- **依赖硬编码 rc 版本 + `--no-save` + 无 lockfile**（全景 L1240-1246）：`@deepseek-ai/dsh-client-ui-primitives@0.2.2-rc.1` 等内部 rc 包被钉死，且安装不进依赖声明，换机 / 升级必崩，且不可复现。
- **主线多次漂移**：从「四件事（自动投递/监测/汇总/界面）」（CHANGELOG L1394）→「关系图自动更新 + 接进插件 + 空间引擎」（全景 L1065）。这是公司自己在 CHANGELOG 里反复警告过的「跑偏」，治理上却没有一个「主线变更留痕 + 旧主线归档」的闸门。
- **规矩自身没有版本收敛**：二十二（先学习）与二十三（至少 2 次搜索）内容重复，二十三是「对二十二的加严」，但二十二没被标记废弃或合并，规则只增不减，长期会变成没人读得完的长文。

## 四、做得好的地方（应当保留）
