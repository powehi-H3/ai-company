## 第 1 搜 · 学知识

**Query**：`event sourcing pattern append only event log aggregation best practices`（docs_code）

**关键结论**（来自 GitHub 多个 event sourcing 实现）：
1. **Event Store 与 State Store 分离**：event store 存全部事件（append-only，system of record），state store 存当前最终状态（物化视图）
2. **append-only**：事件不可变，只追加，天然可审计、可回溯
3. **Replay**：从事件流重新物化出任意时刻的状态
4. **幂等**：同一事件不能重复追加（需要稳定 event id）
5. **CQRS**：读写分离，读侧用查询优化的结构，写侧用追加优化的结构

**对我们的启发**：
- 事件流 = append-only log（机器生成的事件只追加）
- 「当前状态」段 = state store（从事件物化出来的快照）
- 必须有稳定 event_id 去重

## 基于证据的设计（动手依据）

1. **分层**（来自第1搜 CQRS）：
   - `事件流.md` = 人工策展的高质量事件（保留，不覆盖）
   - `事件流-日志.jsonl` = append-only 机器事件日志（新增）
   - 「当前状态」段 = state store 快照
2. **幂等**（来自第1搜）：每条事件带稳定 `id`（来源+标题 hash），重复运行不重复追加
3. **蒸馏而非转储**（来自第2搜 qoli/chatgpt-history）：读对话原文的元数据（标题/来源/消息数/导出时间）+ 产出文件时间戳，生成结构化事件，不塞全文
4. **零依赖**（来自第2搜 tracegram）：纯 Node 内置模块，不装包
