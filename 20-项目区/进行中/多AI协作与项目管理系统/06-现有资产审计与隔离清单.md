# 现有仓库资产审计与隔离清单

- 审计基线：`project/multi-ai-collaboration-foundation`
- 审计日期：2026-11-20
- 范围：原有 AI 公司制度、办公区、正式项目、会议室、档案室、SKILLS、工具脚本和插件源码
- 原则：新系统只继承经过核验的资产与规则；历史材料默认保留但不自动进入执行链。

## 1. 总体判断

原仓库并非纯粹的旧系统废料。它包含组织模型、主体/分身角色资料、桥接适配器、Android 工具、事件流、关系引擎、heartbeat 任务队列、流程引擎和控制台插件等候选基础设施。直接整体删除会破坏新系统可复用的能力和历史证据。

需要隔离的是旧规则的自动执行效力、未经验证的设备状态、重复权威文件和危险脚本行为，而不是简单清空旧目录。

## 3. 已发现并处理的污染源

### 3.1 旧规则被新 AI 入口无条件继承

- 风险：旧规则中的 DSH 独占文件操作、旧设备权限假设和旧目录流转方式，可能覆盖新系统的多 AI / GitHub 分支协作模型。
- 处理：修订 `AI-协作入口.md`，并为 `00-公司规则.md`、`04-项目打包规则.md`、`05-岗位职责规定.md`、`06-产出存放规定.md`、`10-项目归档规则.md` 添加适用边界。
- 结果：保留历史规则，不再将其默认当作新系统执行指令。

### 3.2 能力索引把历史验证写成当前可用

- 风险：`SKILLS.md` 中的“推荐/已验证”可能被新 AI 当作当前设备和所有节点均可用。
- 处理：增加适用边界，明确仓库源码、设备部署、当前实测是三种不同状态；执行前核验节点、权限、依赖和证据。

### 3.3 会议室 README 与实际内容不一致

- 风险：旧 README 称没有会议记录，但目录已有 4 份 2026-11 记录。
- 处理：更新 `30-会议室/README.md`，补齐真实索引和归档规则。

### 3.4 档案室归档规则可能制造重复权威副本

- 风险：旧 README 要求完成项目同时保留两份 ZIP，但目录清单与现状不符，且重复副本可能导致版本分叉。
- 处理：更新 `40-档案室/02-项目备案/README.md`，明确当前只有 README，归档包以项目清单为准；不再自动双份复制。

### 3.5 岗位知识库被误认为权限/系统规则

- 风险：岗位文档含设备路径、root、App 数据库和角色定位，可能被误当作当前权限事实。
- 处理：更新 `40-档案室/05-岗位知识库/README.md`，明确仅作岗位知识，权限必须独立核验。

### 3.6 工具区缺少统一安全入口

- 处理：新增 `60-工具与备份/README.md`，统一工具资产分类、执行前核验和高风险操作门禁。

## 4. 重复内容审计

Git tree 内容哈希检查发现以下重复组：

- 通用开场白在制度模板和多个项目目录重复存放。
- 项目启动清单在制度模板与项目目录重复存放。
- 岗位职责卡与组织设计文件存在完全相同副本。
- DSH 职位白皮书与外部参考评估同时存在项目设计区和岗位知识库副本。
- 推介稿材料在原项目与外部评审项目中存在完全相同副本。
- 两份适配器说明与对应测试日志出现完全相同内容。

处置：这些重复目前可能承担“模板快照、项目随包交付、评审输入、岗位知识副本”等不同用途。没有完整引用与更新责任映射前，不删除任何副本。后续应确立唯一权威源，并将其他副本标记为快照/评审副本/只读引用。

## 5. 办公区与正式项目区的边界

- `10-办公区/<工位>/<项目>/`：AI 的过程记录、任务接收、个人分析和阶段产出。
- `20-项目区/<状态>/<项目>/`：项目的正式需求、计划、决策、测试、权威产出和交付。
- 不能把工位目录中的内容自动视为正式成果；不能把预置 README 当作参与证据。
- 正式成果经项目负责人验收后，应登记到项目权威目录；工位区可保留过程材料并链接正式成果。
- 当前多个工位目录包含仅一行标题的 README 模板。它们是预置工作区占位，不是实际参与证据；不因其存在就认定 AI 已参与项目。

## 7. 桥接与数据安全专项发现

第二轮源码抽查发现，部分桥接工具不仅是“待验证”，而是存在必须先修复的高危问题：

- **S-14 命令注入**：AppAgent 将外部消息文本拼接进双引号 shell 命令，再经 rootc 执行；文本中的命令替换语法可能导致设备 root 命令执行。ACP/AppAgent 真实发送链立即禁用。
- **S-15 私有数据库暴露**：AppAgent 将 App 私有数据库复制到共享存储固定路径，未见可靠清理/权限收紧，并存在并发覆盖。
- **S-16 SQL 标识符注入**：DeepSeek adapter 将 session ID 拼接为 SQL 表名，缺少严格白名单。
- **S-17 脱敏覆盖不足**：sanitize 对通用未加引号密钥格式覆盖不完整，导出数据不得视为已充分脱敏。
- **S-18 回复关联不可靠**：ACP server 用 since=0 和消息总数判断新回复，未校验角色、发送前游标和本次消息关联。
- **S-19 健康状态过度乐观**：adapter health 只检查本地脚本/配置存在，不能证明目标设备实际可发送。

这些问题已登记在根目录 `AI-规则冲突与兼容表.md` S-14 至 S-31，并写入 `SKILLS.md` 与工具区 README 的安全门禁。当前没有修改或执行这些源码。
