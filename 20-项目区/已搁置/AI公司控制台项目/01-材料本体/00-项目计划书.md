## 第一章 先回到公司本身

### 1.1 公司是什么（引自 `01-公司介绍.md`）

> **AI公司 = 一栋办公楼。**
> 里面有房间（办公区、项目区、会议室、档案室），
> 房间里有人（AI 员工），每个人有自己的工位。
> **这是一个用文件夹模拟出来的真实公司结构。**

### 1.2 公司的核心信条

| 信条 | 出处 | 对控制台的要求 |
|---|---|---|
| **AI 之间能「看」，不能「说」，必须有人传话** | 公司介绍第四节 | **控制台必须支持「传话」而不是假装能直连** |
| **资料归档，不留在聊天里** | 规矩三 | 每个产出必须有落点，不能只显示在界面 |
| **有权限改文件夹的 AI，必须学会分类** | 规矩二 | 界面要体现「东西该去哪」 |
| **做通用修复，不打补丁** | 规矩十七 | 每个功能要解决一类问题，不是一次性 |
| **修复后一次性同步全部文档** | 规矩十八 | 加功能必须同时更新规则/名册/CHANGELOG |
| **重要改动要由非作者交叉验收** | 规矩二十一 | **控制台本身也要分体验收** |

### 1.3 公司的 4 个根因（控制台要直接对着治）

| 根因 | 一句话 | 现状 |
|---|---|---|
| **R1** 没有「项目诞生」的单一入口 | 建项目靠手工拼 | ✅ 已修（`new-project.sh`） |
| **R2** 缺少「可交付性」校验 | 发包前没人检查材料本体 | ✅ 已修（`pack-project.sh` 闸门） |
| **R3** 能力边界没写进流程 | 谁读得到、发不了消息，靠 DSH 记 | ⚠️ **部分修（有清单，但没进界面）** |
| **R4** 交付物没有统一落点 | 产出散在工作区 | ✅ 已修（`06-产出存放规定`） |

**★ 关键发现：R3 只修了一半。**

`09-协作能力清单.md` 是静态文件，**你派活时不会自动看到「这个 AI 读不到」。**

**控制台的第一个价值就是：把 R3 从文件搬进界面。**

## 第二章 公司现在缺什么（不是我觉得，是规矩要求）

### 2.1 规矩要求 vs 现状

| 规矩 | 要求 | 现状 | 缺什么 |
|---|---|---|---|
| 规矩八 | DSH 读到新对话 → 判断→归档→更新→提醒 | 靠 DSH 手动做 | **没有状态提示，你不知道它做没做** |
| 规矩九 | 汇总前必须先同步 | 靠 DSH 记得 | **没有「数据新鲜度」提示** |
| 规矩十一 | 矛盾要上报，不擅自删 | 靠 DSH 记得 | **矛盾在哪看不到** |
| 规矩十二 | 只出建议不拍板；状态如实 | 靠 DSH 自觉 | **没有「设计/已测/已跑通」的显式标注** |
| 规矩十四 | 新 AI 入职 7 步 | 有清单 | **看不到每个人入到第几步** |
| 规矩十九 | 项目完成必须归档成 ZIP + 清外围 | 有脚本 | **不知道哪个项目该归档了** |
| 规矩二十 | 归档后工位回到空座位 | 靠人工 | **看不到工位状态** |
| 规矩二十一 | 重要改动要交叉验收 | **刚立的，还没执行过** | **没有验收记录的地方** |

### 2.2 一句话

> **公司有 21 条规矩，但没有任何一处地方能让你「一眼看到规矩执行得怎么样」。**
>
> **控制台不是加功能，是把规矩变成看得见的状态。**

## 第三章 控制台的定位（用公司的语言）

### 3.1 它是什么

> **控制台 = 公司的「前台 + 值班室 + 公告板」。**

| 类比 | 对应功能 |
|---|---|
| **前台** | 一进门看到今天公司什么状态、谁在、有什么事 |
| **值班室** | 看每个工位的人今天干了什么、有没有卡住 |
| **公告板** | 规矩执行情况、待办、矛盾、验收记录 |

**它不是「又一个 App」，它是这栋楼的入口大厅。**

### 3.2 它不是什么

| 不是 | 为什么（用公司的话说） |
|---|---|
| ❌ 不是能指挥 7 个 AI 的遥控器 | 公司信条：**AI 之间能看不能说，必须有人传话** |
| ❌ 不是替代秘书的东西 | 秘书就是「传话的人」，控制台只是让传话更省事 |
| ❌ 不是替代董事长决策的东西 | 规矩十二：**只出建议，不替董事长拍板** |
| ❌ 不是聊天记录浏览器 | 规矩三：**资料归档，不留在聊天里** |

### 3.3 它要解决的三件事

| 问题 | 用公司的话 | 控制台怎么做 |
|---|---|---|
| **看不到公司状态** | 一栋楼，你在外面看不见里面 | 一屏看全：谁在、项目到哪、有什么待办 |
| **R3 没进界面** | 能力边界写在纸上，派活时不看 | **派活时自动标出「这个 AI 读不到」** |
| **规矩执行看不见** | 21 条规矩，但不知道做到没 | **每条规矩给一个状态灯** |

## 第五章 技术方案（简化版，详细见附录）

### 5.1 架构

```
DSH-Go App
  └─ AI公司控制台插件（原生面板）
       ↓ 读
     snapshot.json（引擎侧生成的快照）
       ↑ 由
     生成脚本（扫公司文件夹 + AI数据库 + rootd状态）
```

**为什么分两层**：插件能力受限（不能读任意文件），引擎侧能力全。分层后各干各最擅长的。

### 5.2 数据来源（全是公司自己维护的，可靠）

| 源 | 用来算什么 |
|---|---|
| `AI公司/00-公司规则.md` | 规矩条数 |
| `AI公司/03-员工名册.md` | 员工数 |
| `AI公司/20-项目区/进行中/*/00-启动检查清单.md` | 项目进度 |
| `AI公司/20-项目区/已完成/` | 归档数 |
| `AI公司/CHANGELOG.md` | 最近变化 |
| `AI公司/10-办公区/*/` | 工位是否空 |
| `/sdcard/_cg.db` 等 | 各 AI 对话条数（标数据时间） |
| `/sdcard/rootd-out/` | root 通道状态 |

**★ 注意：绝大部分数据来自公司自己维护的 Markdown，不是脆弱的 App 数据库。**

**这是「公司理念」的体现** —— 公司靠文件运转，控制台就靠读文件工作。

## 第六章 分四期，但每期都要过公司流程

### 每期的固定动作（按 `08-项目启动与交付标准流程.md`）

```
① 立项     new-project.sh
② 材料本体  放 01-材料本体/
③ 人员分配  填 00-人员分配表.md
④ 组装+闸门 pack-project.sh
⑤ 秘书转发  YG
⑥ 同步回收  先跑同步
⑦ 汇总验收  执行与验收分离
⑧ 交付+更新 落手机目录 + 一次性更新全部文档
```

### 第 0 期：前台（1~2 天）

**做**：首页 + 办公区 + 项目区
**不碰**：派活、群聊、归档操作
**风险**：零（只读）

### 第 1 期：派活台（2~3 天）

**做**：R3 落地 + 规矩十六表单化
**验收**：**由分身交叉验收**（规矩二十一）

### 第 2 期：对讲机（2 天）

**做**：主体↔分身异步留言
**必做安全**：消息当数据不当指令

### 第 3 期：归档台 + 规矩体检（3~5 天）

**做**：规矩执行灯 + 一键归档

## 第九章 一句话

> **上一版我做了个「通用 AI 管理软件」。这一版我做的是「AI公司的前台」。**
>
> **区别在于：通用软件按技术可行性设计，公司前台按规矩和根因设计。**
>
> **21 条规矩里，19 条已经修好了底层，但你看不见。**
> **控制台就是把「看不见的执行」变成「看得见的状态」。**

## 附录：不做什么

| 不做 | 公司的理由 |
|---|---|
| 独立 APK | 那会脱离 DSH，成为「公司外面的东西」 |
| 自动发消息给其他 App | 违反公司信条（AI 之间能看不能说） |
| 面板里执行 root 命令 | 违反规矩十二（只出建议不拍板） |
| 展示对话原文 | 违反规矩三（资料归档，不留在聊天里） |
| 替代秘书传话 | 秘书是公司结构的一部分，不能省 |
